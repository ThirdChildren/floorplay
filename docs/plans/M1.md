## Goal

From `public/houses/apartment-a.json` (and `apartment-b.json`) a **1:20 tabletop model** appears in front of the seated
user: floors per room, walls cut at 1 m with the openings, doors and windows as identifiable entities. It is rotated (vertical axis) and enlarged with the **two-hand pinch**; pinching
a room shows the label with name and area computed from the polygon. A ghost hand, without text,
teaches the pinch. Everything verifiable on the PC with repeatable scenarios.

## What exists today and what is missing

- Exists: data of the two homes, schemas, IWSDK configured (`locomotion: false`, `handTracking: true`, `grabbing: true`), IWER emulator.
- **Nothing of the app code exists**: no `StableId`, no `src/logic`, `src/systems`, `src/ui`, `src/data` folders, no store. After M0 the scene is empty.
- Verified in the installed code (not invented):
  - `iwsdk.config.json` accepts `"grabbing": { "useHandPinchForGrab": true }` (type `ProjectGrabbingOptions`); by default the pinch does **not** trigger the grab. `GrabSystem` forwards the pinch as `squeeze` by reading `getSelectStart()/getSelectEnd()` of the hand's gamepad: the same signal that drives `xr_set_select_value` on the emulator.
  - `TwoHandsGrabbable` has the fields `rotate`, `translate`, `scale` (booleans) and `rotateMin/Max`, `translateMin/Max`, `scaleMin/Max` (Vec3); the scale "requires two hands" and the grab is **proximity-based**.
  - `ecs_find_entities` filters by `withComponents` and by `namePattern` (regex on the **name of the Object3D**, max 50 results): **every `StableId` must also become `object3D.name`**, otherwise QA finds nothing.
  - The MCP tools do not navigate to URLs with parameters: see decision D1.

## Project decisions (apply to all tasks)

**D1 · URL parameters and development override.** `browser_interact` "does not navigate to arbitrary URLs": QA can only do `browser_reload_page`. So `parseParams` reads, in this priority order per key: (1) `location.search`, (2) **only in `import.meta.env.DEV`**, the text file `dev-params.local.txt` in the project root, read with `fetch('/dev-params.local.txt')` (it contains the query without `?`, e.g. `house=apartment-b&reset=1&seed=1&debug=1`), (3) defaults. The file is in `.gitignore` and does not end up in `dist/`. If the response is not a valid query (the development server may answer with `index.html` for a missing file), it is ignored. Log: `[soglia] params source=<url|dev-file|default> house=… role=… reset=… seed=… debug=… time=…`. The QA scenarios use this channel: they write the file and do `browser_reload_page`. To be verified in T1.2 that Vite serves the `.txt` file from the root; alternative: `--allow-browser-automation` of `dev up`, or `import.meta.env.VITE_SOGLIA_PARAMS` with a runtime restart.

**D2 · Reference system of the model.** 1 m of plan = 0.05 m in the world (`SCALE = 0.05`). Plan `[x, z]` → world `x`, `z` without inversions (the plan's "up", −z, points away from the user; the side of the entrance faces the user). The center of the plan's bounding box (A: x 0–11, z 0–7.2 → center (5.5; 3.6)) is the origin of `miniature:root`, at floor level. Structure: `miniature:root` (position, Y rotation, uniform scale) → children `house:<id>` (geometry in real metres, shifted by −center) and `table:plinth`.

**D3 · Placement.** At session start (first frame with the head pose; outside a session, with the default camera) the anchor is `head + horizontal_forward × 0.45 m − 0.25 m in y`; `yawDeg` of the model = yaw of the head. With head at (0; 1.2; 0) and yaw 0 → anchor **(0; 0.95; −0.45)**. It depends only on the head pose, not on the floor height (the `local`/`local-floor` reference space is not known: to be verified, but the calculation is relative). Values to be tuned on the headset.

**D4 · Scale and limits.** Initial scale 0.05; zoom limits 0.03 – 0.12 (to be tuned); rotation only around Y (no tipping over); the model does not move (`translate: false`).

**D5 · Wall height.** Walls cut at `CUT_HEIGHT = 1.0` m real (0.05 m on the table). Openings are cut at that height: a door (2.1 m high) becomes a gap over the whole height; a window with `sill` 0.9 m becomes a 0.1 m notch; a window with `sill ≥ 1.0` (bathroom: 1.4 m) leaves no trace in the wall. The `door:*` and `window:*` entities exist anyway.

**D6 · Entities and identifiers (`StableId` = `object3D.name`).**
`house:<id>`, `room:<roomId>`, `wall:<wallId>`, `door:<openingId>`, `window:<openingId>`, `miniature:root`, `table:plinth`, `ui:room-label`, `ui:error-panel`, `ui:ghost-hand-left`, `ui:ghost-hand-right`. The `ui:ghost-hand-*` and `ui:error-panel` entities **exist only while they are visible** (they are created and disposed with `entity.dispose()`), so QA verifies them with `ecs_find_entities`.

**D7 · Store and logs.** `src/logic/state.ts` is the only store (serializable, version 1). Since QA cannot read JS variables, with `?debug=1` every store change writes `[soglia:state] <compact json>`. Log contract (prefix `[soglia]`, level `log`/`warn`, never `error` on the normal path):

| Event | Line |
|---|---|
| parameters | `[soglia] params source=dev-file house=apartment-a role=visitor reset=true seed=1 debug=true time=-` |
| home loaded | `[soglia] house loaded apartment-a rooms=5 walls=13 doors=5 windows=7` (B: `rooms=4 walls=9 doors=4 windows=4`) |
| home missing | `[soglia] house not found: nope` (warn) |
| home invalid | `[soglia] house invalid: <path>: <message>` (warn, one line per error) |
| placement | `[soglia] miniature placed x=0.000 y=0.950 z=-0.450 yawDeg=0.0 scale=0.0500` |
| two-hand gesture | `[soglia] miniature gesture start` / `[soglia] miniature gesture end scale=0.0833 yawDeg=90.0 tiltDeg=0.0` |
| room | `[soglia] room selected living area=23.9`, `[soglia] label shown "Living room & kitchen · 23.9 m²"`, `[soglia] room deselected living` |
| onboarding | `[soglia] onboarding step=pinch` → `step=two-hands` → `step=done` |
| statistics (`debug=1`, every 2 s) | `[soglia:stats] fps=72 calls=34 views=2 callsPerView=17 triangles=6120 geometries=24 textures=0` |

**D8 · Label.** Text = `${name} · ${area.toFixed(1)} m²` (one decimal digit: 23.92 → "23.9"). The `ROADMAP` also cites "24 m²" in the introductory text; scenario S1.3 prevails (23.9 ± 0.1). The label is a UIKit panel, **not** a child of the model (constant size in metres, billboard towards the head), about 0.12 m above the center of the selected room and never beyond 0.6 m from the head; the same panel is reused. If the font does not have the glyphs `·` or `²`, the replacement ("m2") is decided at T1.10 and the scenario is updated.

**D9 · Data validation in the app.** Hand-written function `checkHouse` (no Ajv in the bundle): it checks what the rendering uses and produces readable errors with the field path. Ajv stays only in the tests (T0.3) and a parity test verifies that `checkHouse` and the schema agree on the real files and on the mutations. Alternative if the user prefers it: Ajv at runtime loaded with `import()` only in `?debug=1`.

**D10 · Allowed homes.** Whitelist `KNOWN_HOUSES = ['apartment-a', 'apartment-b']` in `src/data/houses.ts`: an id outside the list generates no network request (avoids a 404 as `error` in the console) and shows the error panel.

**D11 · Materials and colors** in a single place, `src/ui/theme.ts` (M5 will use it for high contrast): wood, tiles, exterior walls, interior walls, base. Solid colors, high contrast between floor and walls; no texture in M1 (no asset to credit in `CREDITS.md`).

**D12 · Strings.** Only in `src/ui/strings.ts`, in English. M1 adds: `roomLabel(name, areaM2)`, `errors.houseNotFound` = "This home could not be found.", `errors.houseInvalid` = "This home file is not valid.", `errors.hint` = "Reload the page or choose another home." No text in the onboarding.
